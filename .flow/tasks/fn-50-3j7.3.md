## Description

Wire the useFocusTrap hook into DialogWrapper for Tab/Shift+Tab cycling. Handle the nested dirty-confirm alertdialog (pause outer trap, activate inner trap).

**Size:** M
**Files:** `src/components/Dialogs/DialogWrapper.tsx`

## Approach

1. Call `useFocusTrap(dialogRef, { enabled: true })` on the main dialog container
2. When the dirty-confirm alertdialog opens (`showConfirm` state):
   - Set `inert` on the outer dialog content (not the whole dialog — just the body + header)
   - Create a separate ref for the alertdialog container
   - Call `useFocusTrap(alertDialogRef, { enabled: showConfirm })` for the nested dialog
3. When dirty-confirm closes: remove `inert` from outer dialog content, focus returns to outer dialog
4. The focus trap must NOT interfere with SettingsSidebar's roving tabindex — `[tabindex="-1"]` elements are already excluded from the focusable selector, so arrow key navigation on inactive tabs is unaffected

## Key context

- DialogWrapper dirty-confirm overlay: lines 128-153 of `DialogWrapper.tsx`, uses `role="alertdialog"`, z-[60]
- SettingsSidebar roving tabindex: `SettingsSidebar.tsx:202` sets `tabIndex={isFocused ? 0 : -1}` — inactive tabs have `tabindex=-1`, excluded from focus trap query
- DmpSectionConfigDialog has 3 separate inline alertdialogs (lines 1651, 1679, 1710) that do NOT use DialogWrapper — out of scope for this task
- Memory pitfall: "E2E keyboard navigation timing — wait for aria-activedescendant to be set before asserting"
