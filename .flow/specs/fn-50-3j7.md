# Focus Management for DialogWrapper

## Problem

DialogWrapper.tsx is the single modal container for all 19 dialogs in CaveChef. Currently it has no focus trap (Tab can escape the modal into the background page), no programmatic initial focus on open, no return-focus on close, and the focus-ring color (#4ecdc4) is hardcoded instead of using a CSS custom property.

## Key Decisions

1. **Custom focus trap hook** — standalone `useFocusTrap(ref, { enabled })` in `src/hooks/useFocusTrap.ts`. No third-party library. Re-queries focusable elements on every Tab keypress to handle dynamic DOM content.

2. **React portal for dialogs** — add `<div id="dialog-root"></div>` to `index.html` (static, after `#root`). DialogWrapper renders into it via `createPortal`. This makes `inert` sibling management trivial.

3. **`inert` on all siblings** — when a dialog opens, set `inert` on all siblings of `dialog-root` (the entire app root). Standard ARIA modal pattern. Managed by a global dialog stack utility. Note: React does NOT allow setting `inert` as a prop — must use ref with `setAttribute`.

4. **Global dialog stack** — `src/utils/dialogStack.ts` exports imperative `pushDialog`/`popDialog`/`isTopmost` functions plus a `useDialogStack()` React hook. Tracks open dialog refs. On mount: push + set inert on app siblings. On unmount: pop + restore inert only if stack empty.

5. **Multiple stacked DialogWrappers** — supported. When dialog B opens on top of dialog A, both the app root siblings AND dialog A's container get `inert`. Only the topmost dialog is interactive. `pushDialog` sets `inert` on all non-topmost dialog containers in the stack. `popDialog` removes `inert` from the new topmost dialog and from app siblings if stack is empty. DOM order (portal append order) determines visual stacking — keep z-50 for all.

6. **Initial focus heuristic** — priority order:
   (a) Element with `[data-autofocus]` attribute (explicit override — highest priority)
   (b) First visible `<input>`, `<textarea>`, or `<select>` in the dialog body (form dialogs)
   (c) Element with `[data-primary-action]` attribute (marks the primary/danger action button)
   (d) First `<button>` that is NOT the close X button
   (e) Fallback: close X button
   Cursor placed at end of text inputs (no auto-select). The `data-primary-action` attribute MUST be added to the primary/danger action button in each dialog (e.g., "Create" in NewProjectDialog, "Delete" in ConfirmDialog, "Export" in ExportDialog).

7. **Focus primary action button** for non-form dialogs. The `data-primary-action` attribute ensures deterministic identification of the primary action button regardless of DOM order. Update SPEC.md Section 11.1 accordingly.

8. **Return focus** — store `document.activeElement` at mount. On unmount, call `.focus()` on stored element if still in DOM. If removed, do nothing.

9. **Escape handler migration** — move from `document.addEventListener('keydown', ..., true)` (capture phase) to `onKeyDown` on the dialog element. Dialog container gets `tabindex="-1"` to ensure it can receive keyboard events. The global handler in `useKeyboardShortcuts.ts` already checks `event.defaultPrevented` (line 301), so DialogWrapper's `e.preventDefault()` in onKeyDown will prevent double-firing. No changes to useKeyboardShortcuts needed.

10. **ContextMenu excluded** — ContextMenu does NOT use DialogWrapper (it's a standalone component at `src/components/common/ContextMenu.tsx`). No changes needed.

11. **Focus ring CSS variables** — `--cc-focus-ring` (color) and `--cc-focus-ring-offset` (offset) defined in `:root`. Root only, no per-component overrides. Replace all hardcoded `#4ecdc4` in focus-visible styles in `index.css`.

12. **Focusable element selector** — comprehensive: `a[href], button:not(:disabled), input:not(:disabled), textarea:not(:disabled), select:not(:disabled), [tabindex]:not([tabindex="-1"]), [contenteditable], audio[controls], video[controls], details > summary`. Excludes elements inside `[inert]` and `[aria-hidden="true"]` subtrees.

13. **Screen reader announcements** — rely on `role="dialog"` + `aria-modal="true"` + `aria-labelledby`. No extra aria-live announcement needed.

14. **Playwright testing** — representative sample of 3-5 dialogs. Use `keyboard.press('Tab')` with both `:focus` selector and `document.activeElement` assertions. Update existing tests broken by portal migration.

15. **React Strict Mode** — effects double-invoke. Focus trap cleanup must handle: clear pending timeouts, remove event listeners, restore inert state. Use `useRef` for mutable state across renders.

## Known Limitations (Out of Scope)

- **DmpSectionConfigDialog** does NOT use DialogWrapper — it renders its own `role="dialog"` div directly (line 993) plus 3 internal `role="alertdialog"` overlays (lines 1651, 1679, 1710). Migrating it to DialogWrapper is a separate effort.
- **LoadingProgress** has `role="dialog"` (line 162) but is a non-interactive progress indicator, not a modal dialog. No focus trap needed.
- **ContextMenu** is a standalone component, not a DialogWrapper consumer. No changes needed.
- **Theme infrastructure** (CSS variable system beyond focus ring) is a separate epic.

## Edge Cases

- Dialog with zero focusable elements (besides close X): focus the close X button
- Trigger element removed while dialog is open: skip return focus, let browser decide
- Keyboard shortcut opens dialog (no button trigger): return focus to whatever had focus (could be map canvas, table cell, etc.)
- Inline-editable table cell triggers error dialog: focus returns to the editing cell after dialog closes
- DmpSectionConfigDialog (complex layout with tabs): focus first input in active tab per standard heuristic
- Nested dirty-confirm overlay: gets its own focus trap instance; outer dialog gets `inert`; on dismiss, focus returns to outer dialog. Initial focus in dirty-confirm follows standard heuristic — `data-autofocus` or `data-primary-action` determines which button gets focus.
- Multiple stacked DialogWrappers: each one pushes to stack, all non-topmost get `inert`, topmost owns focus trap
- Stacked dialog backdrop click: each DialogWrapper has its own backdrop; clicking a backdrop always triggers that specific dialog's requestClose
- Dropdown inside dialog: Select.tsx portals to document.body at z-9999, dialog at z-50. Dropdown renders above dialog. This is existing behavior and acceptable.
- Toast notification: portaled to document.body, z-[99999]. Not a sibling of dialog-root, not affected by inert management.
