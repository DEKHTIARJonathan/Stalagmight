# Data Table Section Dropdown Hover Highlights Section on Map

## Overview

When browsing sections in the DataTable's section dropdown, users lack spatial context for which section they're about to select. This feature adds an `onOptionHover` callback prop to the `Select` component so hovering dropdown options (mouse or keyboard) highlights the corresponding section on the map — matching the existing SectionsPanel hover-to-highlight behavior.

## Scope

**In scope:**
- New `onOptionHover?: (value: string | null) => void` prop on Select component
- Mouse hover on options fires `onOptionHover` with the option's value
- Arrow key / Home / End keyboard navigation fires `onOptionHover` with the highlighted option's value
- Moving between options fires new value directly (no intermediate null)
- Disabled options do not fire `onOptionHover`
- All dropdown close paths fire `onOptionHover(null)`: option selected, click outside, Escape, Tab
- DataTable wires `onOptionHover` to `setHoveredSectionId` for the section dropdown
- Ref-based cleanup on unmount (matching SectionsPanel pattern)
- Playwright e2e tests for hover, keyboard nav, and close-clears behavior

**Out of scope:**
- Auto-firing on dropdown open (initial auto-highlight is not user interaction)
- Debouncing/throttling the callback
- Changes to other Select usage sites (only DataTable section dropdown wires the callback)
- SPEC.md or architecture doc updates (minor feature, not worth doc churn)

## Approach

### Select component changes

Add `onOptionHover` to `SelectProps` interface (after existing props at `Select.tsx:18-37`).

**Mouse hover**: In `renderOption()`, the existing `onMouseEnter` at line 324 already sets `highlightedIndex`. Add `onOptionHover?.(option.value)` call in the same handler, guarded by `!option.disabled`.

**Keyboard navigation**: In the `onKeyDown` handler (lines 219-294), after each case that changes `highlightedIndex` (ArrowDown, ArrowUp, Home, End), resolve the new highlighted option's value and call `onOptionHover?.(value)`. Skip if the resolved option is disabled.

**No intermediate nulls**: Fire the new value directly from event handlers — do NOT use a `useEffect` watching `highlightedIndex` (that would introduce render-cycle delays and risk intermediate nulls).

**Close paths**: Add `onOptionHover?.(null)` call to all existing close code paths:
- `handleSelect()` — option selected via click/Enter/Space
- Outside-click handler (lines 136-148)
- Escape key handler (lines 276-285)
- Tab key handler (lines 287-292)

### DataTable wiring

In `DataTable.tsx`, add an `onOptionHover` handler to the section Select (lines 429-434). The handler converts the string value to a number via `Number(value)` and calls `setHoveredSectionId`. When value is null, call `setHoveredSectionId(null)`.

Follow the ref-based cleanup pattern from `SectionsPanel.tsx:12-30`: track the last hover ID in a ref, clear on unmount only if the store still has the ID this component set.

### Key reuse points

- Hover-to-highlight pattern: `SectionsPanel.tsx:110-122` (mouse enter/leave handlers)
- Ref-based cleanup: `SectionsPanel.tsx:12-30` (lastHoveredIdRef + unmount effect)
- uiStore hover state: `uiStore.ts:541,544` (hoveredSectionId + setter)
- MapCanvas sync: `MapCanvas.tsx:709-714` (useEffect syncing hoveredSectionId to SurveyLayer)
- Keyboard nav: `Select.tsx:219-294` (existing ArrowDown/Up/Home/End handlers)

## Risks / Dependencies

- **fn-31-mhl overlap**: Both modify `Select.tsx`. Changes are orthogonal (portal rendering vs. hover callback prop). Whichever lands first, the other must resolve merge conflicts around the props interface and close handlers. Conflicts should be minor.
- **fn-39-5zr dependency**: Epic scout flagged this as a potential dependency (section highlighting pipeline). Need to verify if highlighting currently works. The spec states "section highlighting already works visually" — if fn-39-5zr is still open, this epic can still land; the callback will fire but the visual effect may not appear until fn-39-5zr completes.
- **SectionId can be 0**: All comparisons must use `!== null`, never truthiness checks. Select option values are strings — conversion via `Number(value)` is safe for 0.
- **Stale closures**: Props in setTimeout callbacks can become stale — track in refs (project memory pitfall).
- **Mouse leave + keyboard focus**: When combining mouse hover and keyboard focus for highlight state, mouse leave handlers must check if keyboard focus is active to avoid clearing the highlight (project memory pitfall).
